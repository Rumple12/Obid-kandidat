\section{Implementation}\label{sec:implementation}

\setlength{\emergencystretch}{2em}

This chapter describes the frozen implementation and applies the provenance
vocabulary defined in Table~\ref{tab:method-provenance} to its components.

\subsection{System Overview}\label{subsec:impl-overview}

The final system has two executable configurations at the same temperature
and fan boundary. \texttt{CONFIG-BASELINE} is the inherited minimal-agent
comparator. \texttt{CONFIG-OBID} extends the decision path with one Decision
Agent, two read-only tools, bounded memory, structured internal decisions,
post-agent validation, deterministic policy, and an executable
human-in-the-loop (HITL) gate. Both configurations ultimately select the
existing Yacoub middleware route for the simulated fan.

Within \texttt{CONFIG-OBID}, the Decision Agent uses read-only threshold and
state information to return a candidate action or internal
\texttt{no\_action}. The following sections describe how validation, policy,
and conditional HITL determine whether a candidate can reach an inherited fan
route.

\subsection{Yacoub-Compatible Boundary}\label{subsec:impl-integration}

The active middleware is the Python implementation inherited from the frozen
Yacoub repository at commit
\texttt{\seqsplit{278318340bfa4e4650a97a2baba73f63bd868ed9}}. Obid did not
reimplement or copy this service. The middleware runs on the host at port
8000. Host-side clients address it through \texttt{127.0.0.1:8000}, while
Dockerized n8n reaches the same process through
\texttt{host.docker.internal:8000}. The source default binds to
\texttt{127.0.0.1}; the verified runtime used a host-binding override so that
the n8n container could reach it without changing route or payload semantics.

Four inherited routes form the compatible interface. \texttt{GET /status}
reports the in-memory fan and hardware state.
\texttt{POST /sensor-event} normalizes and forwards sensor input. The simulated
fan state changes through \texttt{POST /fan/on} and \texttt{POST /fan/off}.
The Decision Agent's status tool calls only the first route. After a
candidate has been authorized, deterministic routing selects one of the two
fan-action routes. The evaluation configurations can also receive events
directly at their n8n webhooks; consequently, not every evaluated input passes
through the inherited \texttt{/sensor-event} normalization path. The Python fan
endpoint itself does not consume the four-field action as an HTTP request body.

The implementation preserves the exact sensor/action contracts, target
\texttt{fan\_1}, and inclusive threshold rule defined in
Section~\ref{subsec:method-scenario}. The shared action contains neither a risk
field nor an internal \texttt{no\_action} value.

This threshold and its action meanings are Yacoub-owned semantics. Obid's
contribution is the agentic decision and runtime reliability behavior around
that unchanged rule. The inherited middleware's empty-body and empty-object
normalization is also distinct from Obid validation: it can create a default
temperature event and therefore cannot be used as evidence that the Obid
decision layer rejected malformed input.

\subsection{Inherited Minimal Agent Baseline}\label{subsec:impl-baseline}

\texttt{CONFIG-BASELINE} is the executable inherited minimal-agent comparator
used for the RQ3 comparison. Its portable workflow is
\codepath{cognitive\_logic/baselines/yacoub/minimal-agent-baseline.json},
with workflow ID \texttt{agent-minimal}. It receives an event at its n8n
webhook, serializes the request body as the model input, and invokes one Basic
LLM Chain connected to one Google Gemini Chat Model node. The inherited prompt
asks for one four-field action under the same inclusive threshold rule.

The next Code node performs minimal output handling rather than contract
validation. It selects an observable text-like model field, extracts a
JSON-looking object when needed, and calls \texttt{JSON.parse}. Two successive
branches inspect \texttt{action\_id}: \texttt{fan\_on} selects
\texttt{POST /fan/on}, \texttt{fan\_off} selects
\texttt{POST /fan/off}, and any other parsed value reaches an unrouted
fallback. The workflow has no post-agent JSON Schema validator, deterministic
Obid policy, retry or repair loop, approval gate, or HITL mechanism.

The baseline is stateless. It has no memory node, memory connection, buffer,
vector store, or persistent workflow state. Its prompt, one-decision
architecture, parser, routing, and no-memory choice are
\texttt{YACOUB\_INHERITED}. Obid-created work for this configuration is
limited to reconstruction of the missing historical model connection,
portable sanitization, and verification. The historical workflow stored
\texttt{options: \{\}} and omitted \texttt{modelName}; the effective
\codepath{models/gemini-2.5-flash} value was recovered from the matching pinned
node default and made explicit in the sanitized export. The exact prompt was
also embedded in the executable System message because a repository-path
reminder cannot supply prompt text to a running LLM node.

The separate deterministic threshold workflow remains an inherited
development and compatibility anchor. It is not a third core configuration
and is not the RQ3 comparator. This distinction prevents deterministic
execution from being misrepresented as the baseline against which
\texttt{CONFIG-OBID} was evaluated.

\subsection{CONFIG-OBID Decision Agent}\label{subsec:impl-agent}

The authoritative Obid workflow is
\texttt{CONFIG-OBID - Single Agent v3 HITL}, with workflow ID
\texttt{obid-agent-v3-hitl}. It combines the final cognitive path,
runtime-safety subworkflow, caller-side policy routing, and embedded HITL
gate. The workflow contains one n8n AI Agent v3 node and one Gemini model
node \cite{n8nAIAgent,n8nGeminiChatModel}. There is no second model, validator
agent, or multi-agent exchange.

At ingress, a deterministic Code node prepares the event and checks the
minimum conditions needed by the decision layer. The request body must be an
object; \texttt{sensor\_id} and \texttt{timestamp} must be non-empty strings;
\texttt{type} must equal \texttt{temperature}; \texttt{value} must be a
finite number; \texttt{unit} must equal \texttt{C}; and the synthetic
\texttt{X-Obid-Session-Id} header must be non-empty. A failed check terminates
at \texttt{OBID\_INPUT\_HANDLING} before the model, memory, tools, safety
component, or endpoints can run. This gate is not a complete sensor-schema
validator: for example, it does not validate the timestamp's date-time format
or reject additional sensor fields.

For a valid event, the prepared JSON becomes the agent input. The agent is
connected to the model, the two-interaction memory, and exactly two tools.
After the final response, a Code node extracts the internal decision envelope.
An internal no-op terminates locally. A non-null candidate is labelled at the
\texttt{OBID\_POST\_AGENT\_PRE\_VALIDATOR} boundary and sent synchronously to
the final runtime-safety component. Only a released action can reach the
caller-side endpoint branches.

\subsection{System Prompt and Structured Decision Envelope}\label{subsec:impl-prompt}

The Obid system prompt defines the Decision Agent as one controlled
temperature-event agent for \texttt{fan\_1}. It repeats the inherited
threshold, limits the action vocabulary to \texttt{fan\_on} and
\texttt{fan\_off}, and instructs the agent to use only the two connected
tools. The threshold tool must be called once for each valid event. The latest
usable remembered \texttt{state\_after} should be used as current state;
otherwise the status tool should be called once. When desired and current
state match, the prompt instructs the agent to suppress the duplicate action.

The prompt also imposes output discipline. It requests one JSON object without
Markdown, prose, private data, or hidden reasoning. A state change is expressed
through \texttt{decision: emit\_action}; an already satisfied state is
expressed through \texttt{decision: no\_action}. These instructions constrain
model behavior but do not by themselves guarantee runtime correctness. The
separate validator and policy provide the deterministic post-agent controls.

The internal envelope contains five fields. The \texttt{decision} field records
the outcome, while \texttt{action} holds a candidate or null.

The {\small\texttt{state\_before}} and {\small\texttt{state\_after}} fields
record state. The {\small\texttt{reason\_code}} field records the associated
reason code.

For \texttt{emit\_action}, the nested action contains \texttt{action\_id},
\texttt{target}, and \texttt{reason}.

The fourth shared action field is \texttt{requires\_approval}. For
\texttt{no\_action}, \texttt{action} is null. The no-op is therefore an
internal representation of absent release, not an additional shared action
identifier. It bypasses the safety subworkflow and cannot select a middleware
action endpoint.

The envelope parser is deliberately tolerant at this cognitive boundary. It
can extract JSON from a fenced response or from the first apparent object and
then projects the five envelope fields. It does not strictly validate the
entire internal envelope. Strict runtime validation is applied later to a
non-null nested action candidate. This separation avoids describing prompt
formatting or tolerant extraction as equivalent to enforcement of the shared
action contract.

\subsection{Controlled ReAct Execution}\label{subsec:impl-react}

The AI Agent implements a controlled ReAct-style, tool-mediated execution
cycle. A cold-state event can require a threshold lookup, a status lookup, and
then a final decision \cite{yao2023react}. The node's \texttt{maxIterations} setting is 3. This is
the smallest installed bound that permits those two sequential tool rounds,
followed by the final response. When recent memory already contains a usable
state, the status lookup is omitted and only the threshold tool is needed.

The prompt limits each tool to one call for the current event and prohibits
other tools. The workflow supplies no retry loop, self-repair path, fallback
model, recursive agent, or dynamically created tool. A formatting or
tool-selection failure is retained as an execution outcome rather than being
silently repaired by another model call.

Only observable execution data is used to describe this loop. Tool-node
inputs, results, ordering and counts, the final structured response, node
status, and the configured iteration bound can be inspected.
The \texttt{returnIntermediateSteps} setting and streaming are disabled. The
implementation neither requests nor stores hidden chain-of-thought, private
scratchpad content, or an internal reasoning trace.

\subsection{Bounded Memory}\label{subsec:impl-memory}

State reuse is implemented with one n8n Simple Memory node. Its identifier is
\texttt{memoryBufferWindow}, and its type version is 1.3.

The \texttt{contextWindowLength} setting is 2, meaning that the model-visible window
contains the two latest completed input/final-output interaction pairs
\cite{n8nSimpleMemory,wang2024surveyagents,liu2024lostmiddle}. Tool
calls inside an interaction do not consume separate memory slots. This gives
the agent access to recent \texttt{state\_after} values without introducing a
second memory strategy or long-term retrieval system.

The memory uses \texttt{sessionIdType: customKey} and the expression
\texttt{=\{\{ \$json.session\_id \}\}}. The input-preparation node derives
that value from the synthetic \texttt{X-Obid-Session-Id} header, leaving the
shared five-field sensor body unchanged. Reusing a session ID makes recent
state available across related events; a new ID creates logical isolation for
another sequence.

This memory is process-local. It persists across executions only while the
same n8n process remains alive, is lost on restart, and is therefore not
durable storage. The documented node behavior also removes inactive session
buffers after one hour when cleanup next runs. Older messages can remain in
the underlying history even when they are outside the active two-interaction
load. Leaving the model-visible window must not be interpreted as physical
deletion. The implemented purpose is bounded recent-state reuse and duplicate
action suppression, not permanent history, a database-backed memory claim, or
a comparison of memory techniques.

\subsection{Runtime Action Validation}\label{subsec:impl-validator}

A candidate action crosses the named post-agent, pre-validator boundary. The
reusable safety workflow receives it there. The final workflow,
\texttt{runtime-safety-v2-hitl}, preserves the validator introduced in
\texttt{runtime-safety-v1}. It accepts either a candidate object or a raw JSON
string. A string is parsed once with \texttt{JSON.parse}; there is no trimming,
retry, model repair, normalization, default insertion, or type coercion. A
parsed value must be a plain, non-null, non-array object.

The validator records the received form, parse status, parsed value, complete

frozen four-field schema. The pinned n8n Code-node environment did not expose
a suitable ordinary external JSON Schema validator without changing the
runtime. The implementation enforces the constraints present in this one
contract; it is not a general JSON Schema engine, general security filter, or
production-safety mechanism
\cite{wright2022jsonschemavalidation,schneider2000enforceable}.

exact internal object. Its injection seam is
{\small\texttt{OBID\_POLICY\_INPUT}}.

{\small\texttt{POLICY-HITL-REQUIRED}}. The
{\small\texttt{approval\_required}} value is true. The
{\small\texttt{shared\_contract\_field}} value is false.

This context is evaluated only after the original action has passed

schema.

release. An invalid candidate stops before context handling, policy, and
HITL, so human approval cannot rescue \texttt{fan\_reverse}, an unknown
target, or any other contract-invalid value. For direct release, the caller
requires both \texttt{schema\_valid: true} and policy decision
\texttt{allow}. It then maps the released \texttt{action\_id} to exactly one
inherited fan endpoint.

\subsection{HITL Runtime}\label{subsec:impl-hitl}

An \texttt{APPROVAL\_REQUIRED} safety result activates the final HITL gate in
the caller. Entry requires a schema-valid action, an executed
approval-required policy, a valid four-field held action
whose approval flag is true, a null released action, and a successful
policy-transformation integrity check. Failed preconditions terminate without
creating a form.

The gate uses \texttt{n8n-nodes-base.wait} type version 1.1 in
\texttt{resume: form} mode, with no configured wait limit \cite{n8nWait}. Before waiting, a
Code node deep-copies the held action and stores a four-field snapshot. It
also creates a synthetic request ID of the form
\texttt{hitl-<execution-id>}. The form displays the action, policy reason, and
policy case as read-only review information. The reviewer submits exactly one
required field, \texttt{human\_decision}, whose permitted values are
\texttt{approve} and \texttt{deny}; the action fields are not editable form
inputs.

While the execution is pending, \texttt{released\_action} remains null and no
fan endpoint is eligible. After resume, finalization retrieves the persisted
pre-wait action rather than reconstructing it from form data. It compares
\texttt{action\_id}, \texttt{target}, \texttt{reason}, and
\texttt{requires\_approval} with the stored snapshot and rejects unexpected
submitted fields. Exact approval with an unchanged held action releases that
same action, still carrying \texttt{requires\_approval: true}. Denial releases
null. Invalid decisions, integrity failures, and failed preconditions also
release null. Approval is thus separate runtime authorization rather than a
rewrite of the shared action
\cite{amershi2019guidelines,nist2023airmf}.

The workflow records start, request, decision, and completion timestamps.
From these it derives pre-wait automation, human wait, post-decision
automation, and total elapsed time as separate fields. The implementation
does not require or store reviewer identity, a credential, or a transient form
resume URL in the committed evidence.

The first bounded topology placed the native Wait/form inside the standalone
\texttt{runtime-hitl-v1} child workflow. The child waited and produced an
approved output. In n8n \texttt{1.123.37}, however, the synchronous parent
resumed with the child's pre-wait input rather than its post-wait result. The
parent could not establish release authorization and therefore failed closed.
The retained child artifact records this compatibility limitation.

The final repair embeds the same precondition, request, Wait, finalization,
and integrity behavior directly in \texttt{CONFIG-OBID} v3 and the HITL
harness. Only placement changed. The contract, policy, decision vocabulary,
held-action checks, and endpoint-release conditions remained the same.

\subsection{Summary of Implementation}\label{subsec:impl-summary}

The frozen implementation adds a bounded Obid decision path and executable
validation, policy, and HITL controls to the unchanged shared action boundary.
Its controlled seams and evaluation tooling preserve attributable attempts,
locked processing, and traceability without changing inherited authorship.
