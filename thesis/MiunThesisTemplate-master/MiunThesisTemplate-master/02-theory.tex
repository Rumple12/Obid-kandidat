\section{Theory and Related Work}\label{sec:theory}

This chapter introduces the workflow, agent, runtime-control, evaluation, and
related-work concepts used by the project-specific chapters that follow.

\subsection{Workflow Automation and Orchestration}\label{subsec:theory-workflow}

A workflow represents work as connected activities with explicit control flow.
Common patterns include sequence, conditional routing, parallel branches,
synchronization, repetition, and cancellation. Workflow languages differ in
which patterns they can express, even when their diagrams look similar
\cite{vanderaalst2003workflowpatterns}. A workflow therefore defines when an
activity may run, the data it receives, and the path that follows.

Orchestration coordinates several components or services. A process may receive
an event, transform its data, invoke a decision service, and pass an accepted
outcome to an action service. Service-oriented computing places these
capabilities behind interfaces, avoiding the need to combine every
responsibility in one component \cite{papazoglou2003serviceoriented}. Execution
may be sequential when stages depend on one another or event-driven when a
trigger starts data- or state-dependent routing.

Explicit stages provide observable execution boundaries. They show where a
proposed action was transformed, rejected, held, or released and allow the same
flow to run under controlled inputs. Here, orchestration provides the execution
environment; the particular architecture remains a project-specific choice.

\subsection[n8n and Low-Code Workflow Automation]{n8n and Low-Code Workflow\\Automation}\label{subsec:theory-n8n}

Low-code platforms let developers assemble applications and integrations from
graphical elements, configuration, and small pieces of code. Platforms vary in
their users, abstractions, extensibility, and deployment models, so low-code is
not a single engineering method \cite{bock2021lowcode}.

n8n represents workflows as connected nodes. During development, a workflow can
run manually; once published, it can respond to triggers such as an incoming
webhook. n8n also supports self-hosted deployment
\cite{n8nCreateRunWorkflows,n8nHosting}. These features make it suitable for
visually assembling and inspecting an event-driven workflow.

The executable configuration still includes node settings, expressions, code,
credentials, and platform versions. Visual control flow alone does not establish
the reliability of the decisions passing through it.

\subsection{IoT Event-Action Systems}\label{subsec:theory-iot}

An Internet of Things (IoT) system connects sensor observations to software
services and physical or simulated actuators. A sensor event usually combines a
measured value with context such as time, identity, location, or unit.
Context-aware systems use this information to characterize a situation before
selecting a response \cite{perera2014context}. Control therefore concerns the
relation between an event, current state, a decision, and an allowed action, not
only the measurement.

Trigger-action programming expresses a simple form of this relation: when an
event occurs, perform a specified action. Large collections of end-user
automations show how events from services and devices can initiate actions across
different channels \cite{ur2016triggeraction}. A controlled system can add a
decision stage that consults state, declines to act, or requests authorization
before crossing the actuator boundary.

An observable action boundary records whether a command was emitted, its target,
and the resulting state. A simulator makes such observations repeatable without
the variability or practical risk of a physical actuator. It can test control
logic and interfaces, but not electrical faults, network conditions, device
timing, or physical consequences. The later temperature-to-fan setting is
therefore a bounded event-state-action example.

\subsection{Middleware and API Boundaries}\label{subsec:theory-middleware}

Middleware separates application components from lower-level communication.
Decision logic need not contain device-communication details, and an action
service need not know how a decision was produced. Service-oriented designs use
described interfaces for this interaction \cite{papazoglou2003serviceoriented}.

An application programming interface (API) defines available operations,
messages, and response behavior \cite{papazoglou2003serviceoriented}. A stable
contract lets independently owned components agree on fields, meanings, and
errors while keeping proposal and execution responsibilities separate.
Compatibility requires both transport and semantic agreement: successful HTTP
delivery proves only that a request was exchanged. The project's inherited and
shared boundary is defined formally in Table~\ref{tab:method-provenance}.

\subsection{Structured Data and JSON Contracts}\label{subsec:theory-json}

JavaScript Object Notation (JSON) is a textual, language-independent data
interchange format built mainly from objects with named members and arrays with
ordered values \cite{bray2017json}. It lets services exchange structured values
without sharing a programming-language object model. Parsing establishes only
that a document uses valid JSON syntax.

A data contract adds structural and semantic expectations. It can require
properties, constrain their types, limit values to an enumeration, and reject
additional properties. JSON Schema defines vocabularies for these assertions,
including \texttt{type}, \texttt{required}, \texttt{const}, and \texttt{enum}
\cite{wright2022jsonschemavalidation}. A string used where a numeric measurement
is required may therefore parse as JSON while violating the contract.

Contract validation is narrower than authorization. A schema-valid command and
target may still be inappropriate in the current state, while a malformed
message should be rejected before policy interprets it. The resulting sequence
is: parse the representation, validate the contract, and then decide whether the
valid candidate may be released.

Contracts also support compatibility as interfaces evolve. Producers and
consumers must agree on required fields, allowed values, versioning, and rejection
behavior; otherwise, valid JSON may still break interoperability. A schema does
not encode every operational hazard, false input, or authorization rule.

\subsection{LLM Agents and Agentic Workflows}\label{subsec:theory-agents}

A large language model (LLM) generates output from supplied context. An agentic
workflow adds a control process that uses the model to pursue a task through an
environment. Common components include instructions, context, memory, decision
logic, actions or tools, and returned observations \cite{wang2024surveyagents}.
This differs from requesting one isolated model response.

The surrounding workflow selects context and tools, returns tool results, limits
cycles, and determines termination. This can combine language-based decisions
with live or deterministic information, but the model may still choose an
unsuitable tool, produce invalid arguments, repeat an action, or rely on stale
context.

Agent behavior therefore combines probabilistic generation with deterministic
surroundings. Bounded tools and iterations, validation, policy, and release rules
can enforce limits that instructions alone cannot. A workflow can thus make
several tool-assisted decisions while remaining restricted to a narrow action
vocabulary and human approval.

Chapter~\ref{sec:implementation} defines the project's bounded tools, memory,
and release path.

\subsection{ReAct and Tool Use}\label{subsec:theory-react}

ReAct combines task-oriented model output with actions that obtain observations
from an environment. Interleaving reasoning-oriented text and actions lets a
model update its next step after receiving external information
\cite{yao2023react}. In an executable workflow, the observable cycle is action
selection, tool invocation, returned observation, and either another bounded
cycle or a terminal response. This description does not require private model
reasoning.

A tool exposes an external capability as a named operation with defined input
and output, such as retrieving a threshold or reading current state. A restricted
interface narrows the action space and makes calls observable, but it cannot
ensure that the model chooses the right tool or uses its result correctly.
ToolEmu likewise treats tool access as a capability whose consequential failures
require explicit testing \cite{ruan2024toolemu}.

Iteration bounds prevent indefinite calls and resource use, although a limit can
also end an incomplete task. Tool permissions and cycle limits therefore define
the interaction boundary.

Here, ReAct-style behavior means a controlled action-tool-observation pattern.
Tool use does not release an action: a separate path decides whether the candidate
may cross the action interface.

\subsection{Memory in LLM-Agent Workflows}\label{subsec:theory-memory}

Memory in an LLM-agent system can mean selected prior interactions in the current
prompt or information retained externally across sessions. Agent surveys
distinguish bounded context from persistent stores and describe windowing as one
way to limit short-term history \cite{wang2024surveyagents}. As a contrasting
example, Reflexion retains feedback in episodic memory to guide later attempts
without updating model weights \cite{shinn2023reflexion}.

A bounded window controls context growth but discards older information. Session
identity determines which interactions are grouped; shared sessions can mix
unrelated context, while a new session cannot recover process-local history that
was never persisted.

Longer context is not always more useful, especially when relevant information
appears away from the beginning or end \cite{liu2024lostmiddle}. Memory can also
become stale after an external device changes. Remembered state records a prior
interaction, whereas a live observation provides newer evidence about the
environment.

Chapter~\ref{sec:implementation} implements one recent, session-scoped,
process-local memory strategy.

\subsection[Structured Output and Runtime Validation]{Structured Output and\\Runtime Validation}\label{subsec:theory-validation}

Structured output asks a model for data that a program can parse instead of
unrestricted prose. An envelope can place the action, target, explanation, and
control flags in explicit fields. Instructions and examples may improve
conformity, but the object remains a candidate until executable code checks it.

Structure can be enforced at two stages. Generation-time constraints limit
decoding to strings accepted by a grammar; grammar-constrained decoding can
guarantee formal structure without fine-tuning \cite{geng2023grammar}.
Post-generation validation receives the produced value, parses it, and checks
assertions such as required fields, types, constants, and enumerations
\cite{wright2022jsonschemavalidation}. The approaches can complement each other
but remain distinct.

Runtime validation is deterministic when the same candidate and schema always
give the same result. An invalid candidate should be rejected before reaching an
action endpoint. Repair or coercion is separate behavior that can hide the
original output; strict rejection instead preserves a clear boundary between a
probabilistic proposal and the executable interface.

Structural validity does not imply authorization. A well-formed command can rely
on false data, violate policy, or be unsafe in its physical context. Nor can a
schema judge the truth of a non-empty explanation. Chapter~
\ref{sec:implementation} therefore treats the validator as a contract-specific
runtime control, separate from policy and operational safeguards.

\subsection{Deterministic Safety Policies}\label{subsec:theory-policy}

After structural validation, a policy determines whether a candidate may
proceed. Explicit rules over a valid action and its context can produce allow,
block, or approval required. Allowlists restrict
actions and targets, while contextual rules can require additional authority.

Runtime enforcement separates proposal from authorization. Schneider describes
execution monitoring as stopping execution before a specified policy violation
\cite{schneider2000enforceable}. At this narrower boundary, a deterministic gate
can block an action despite any natural-language argument for an exception.

Such a policy recognizes only encoded rules and supplied context; it cannot
discover unknown hazards, and its rules can become outdated. Its value lies in
inspectable, repeatable release control. Chapter~\ref{sec:system-design}
explains why the project places this gate after validation.

\subsection{Human-in-the-Loop}\label{subsec:theory-hitl}

Human-in-the-Loop (HITL) control gives a person authority at a defined decision
point. For action release, a candidate can be pending, approved, or denied.
Pending keeps it held, approval permits it to continue, and denial ends the path.
This differs from notifying a person after an automated action.

Human-AI guidance recommends making capabilities and consequences clear while
allowing users to dismiss or correct outputs \cite{amershi2019guidelines}. A
reviewer can add context and judgment unavailable to a fixed policy, but the
workflow must identify the authorized reviewer, the held candidate, and whether
approval may modify it. Records should connect proposal, human decision, and any
released action.

Review also adds variability. Workload, delay, interface clarity, and trust in
automation can affect decisions. People adjust trust according to how they
understand an automated aid's successes and failures, and weak understanding can
support inappropriate reliance \cite{dzindolet2003trust}. Human review can also
become the main source of elapsed time.

Human oversight is therefore not sufficient by itself. Invalid candidates should
fail validation first, and pending must prevent release. The later evaluation
uses this executable meaning of HITL rather than treating the sessions as a
general usability study.

\subsection[Reliability Evaluation of LLM and Agent Systems]{Reliability Evaluation of\\LLM and Agent Systems}\label{subsec:theory-reliability}

Reliability can be evaluated against an oracle that defines the expected terminal
outcome for a given input. Correctness asks whether an attempt matches that
outcome; consistency asks whether repetitions produce the same normalized
outcome. A system may therefore be consistently wrong or reach the correct result
through variable intermediate behavior.

Agent evaluations often combine models, scaffolding, tools, and costs. Kapoor et
al. call for standardized, reproducible evaluation that considers efficiency as
well as task success \cite{kapoor2025agentsmatter}. Comparisons should therefore
name each complete configuration and avoid assigning a difference to one
component without an isolating ablation.

Repeated evaluation reveals observed variability. Chapter~\ref{sec:method}
defines the repetition protocol. Small samples support descriptive counts and
summaries, not statistical significance or population failure rates. Latency
likewise requires declared start and end events, and complete configurations may
perform unequal work. Chapter~\ref{sec:method} defines the study's concrete
oracle, timing, and traceability rules.
