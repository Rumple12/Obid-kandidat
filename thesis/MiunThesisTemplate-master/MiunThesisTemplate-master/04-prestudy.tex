\section[Choice of Approach / System Design]{Choice of Approach /\\System Design}\label{sec:system-design}

This chapter explains why the final Obid architecture was selected to add an
agentic decision and reliability layer while preserving the completed
Yacoub-compatible workflow-to-action system. Detailed research methods are
presented in Chapter~\ref{sec:method}, while the executable implementation is
described in Chapter~\ref{sec:implementation}.

\subsection{Design Goals and Constraints}\label{subsec:design-goals}

The design was derived from RQ1--RQ3, stated in
Section~\ref{subsec:intro-rqs}, rather than from a desire to include as many
agent features as possible. Each question places a different requirement on the
architecture.

To make the normal, malformed, and state-dependent RQ1 cases explicit and
observable, the selected design goes beyond a single model call that maps a
temperature value to an action. It accepts a controlled event, exposes the
inherited threshold as a deterministic tool, observes current state, retains a
small amount of recent state, and returns a machine-readable decision.
Malformed input also terminates at an Obid-owned boundary so that its
handling can be attributed to the evaluated decision layer rather than to
normalization in inherited middleware.

RQ2 changes the role of the model output. An agent response is treated as a
candidate, not as authorization to actuate the shared interface. Deterministic
validation and policy must therefore remain downstream of the Decision Agent.
The architecture also needs a real pending state and an executable human
approval or denial path; approval described only in documentation would not
provide the runtime behavior asked about in RQ2.

RQ3 requires two clearly identified configurations at the same collaboration
boundary. \texttt{CONFIG-BASELINE} is the inherited minimal-agent comparator,
whereas \texttt{CONFIG-OBID} is the extended configuration. Both retain the
same primary model identifier, event and action semantics, and inherited action
boundary. This keeps the comparison focused on the selected workflow designs
rather than on differences between model families or device platforms. The
separate inherited deterministic workflow remains a useful engineering anchor,
but it is not the RQ3 comparator.

\subsection{Inherited Collaboration Boundary}\label{subsec:design-boundary}

The design preserves the \mbox{\texttt{YACOUB\_INHERITED}} and
\mbox{\texttt{SHARED\_INTERFACE}} bands defined formally in
Table~\ref{tab:method-provenance}. The latter describes compatibility, not a
transfer of authorship.

Preserving that boundary served four purposes. First, it allowed the Obid layer
to join the existing system without rebuilding infrastructure unrelated to the
research questions. Second, it retained compatible event, action, target, and
endpoint meanings across both evaluated configurations. Third, it made the RQ3
comparison more controlled because \texttt{CONFIG-BASELINE} and
\texttt{CONFIG-OBID} act on the same simulated device boundary. Fourth, it
isolated the Obid contribution: stronger cognition and runtime release control
could be discussed without absorbing inherited middleware or hardware work into
the authorship claim.

The contracts and semantics defined in
Section~\ref{subsec:method-scenario} remain unchanged. Obid therefore extends
the system around the shared boundary rather than extending the contracts.

The boundary also clarifies where action authority resides. The Decision Agent
does not call physical hardware and its read-only tools do not execute fan
actions. After an action has passed the Obid release controls, deterministic
routing selects the inherited middleware action endpoint. The observable device
in this thesis is the inherited simulated fan. Existing Raspberry Pi and
action-side evidence remains Yacoub-owned context and is not new Obid hardware
validation. Implementation details for this boundary are given in
Section~\ref{subsec:impl-integration}.

\subsection{Chosen Agentic Architecture}\label{subsec:design-architecture}

The selected \texttt{CONFIG-OBID} architecture begins with a sensor event or a
controlled test event at an Obid-owned ingress. Deterministic input handling
checks the minimum conditions needed by the decision path. A valid event is
then supplied to one Decision Agent connected to one Gemini model node using
the frozen primary configuration, exactly two read-only tools, and one bounded-memory
configuration. The agent produces either a structured action candidate or an
internal \texttt{no\_action} decision.

An action candidate next crosses from cognition to deterministic release
control. It is parsed and checked against the frozen shared action contract. A
contract-invalid candidate is blocked before policy executes. Only a valid
candidate reaches policy, which can allow direct release, block defensively, or
require approval. Across these stages, the release-control outcomes are
\texttt{ALLOW}, \texttt{BLOCK}, and \mbox{\texttt{APPROVAL\_REQUIRED}}. An
approval-required action is held until the executable HITL gate records an
approval or denial. Approval releases the action unchanged from that held
snapshot. Only an authorized release can select an inherited fan endpoint. An
internal no-op terminates before a shared action is formed.

This ordering separates three concerns: the model proposes, deterministic
controls authorize, and inherited middleware performs the simulated action.
The concrete workflow nodes and wiring are documented in
Chapter~\ref{sec:implementation}.

The complete path and its provenance boundary are shown in

\subsection{Tool-Use and Controlled ReAct Design}\label{subsec:design-react}

Exactly two tools were selected because the scenario requires two kinds of
information and neither should grant release authority. The threshold tool,
\mbox{\texttt{temperature\_threshold\_tool}}, performs the inherited calculation
deterministically. It reports the relation to the threshold and the
corresponding desired fan state, but it does not read or change middleware
state. The status tool, \mbox{\texttt{fan\_status\_tool}}, reads the current
simulated state through the inherited \texttt{/status} boundary. It cannot
choose another device or call an action endpoint.

This division separates calculation and observation from actuation. The agent
may use the threshold result to identify the desired state and the status result
to identify current state, but endpoint release is decided later. Keeping both
tools read-only reduces the number of paths through which a model-generated
tool call could mutate the system and makes the observable interaction easier
to attribute.

The controlled ReAct-style cycle is correspondingly small
\cite{yao2023react,wang2024surveyagents}:

\begin{center}
event $\rightarrow$ threshold calculation and, when memory is cold, status observation
$\rightarrow$ final structured decision.
\end{center}

The prompt permits one threshold-tool call and, when needed, one status-tool
call for the current event. The configured iteration bound is
\texttt{maxIterations: 3}. This permits a cold-state event to use the threshold
tool, obtain status when recent state is unavailable, and still return a final
answer. When usable recent state exists, the status lookup can be omitted. The
design records configured bounds and
observable tool names, inputs, outputs, order, and counts. It does not use or
claim access to hidden chain-of-thought or private model reasoning.

\subsection{Bounded-Memory Design}\label{subsec:design-memory}

State dependence in the selected scenario is narrow but real. A cold session
may need a status lookup before deciding whether a fan action is necessary. A
recent finalized decision envelope can provide a usable model-visible
\mbox{\texttt{state\_after}} for the next event, allowing a duplicate action to be
suppressed. This is remembered decision state rather than independent
verification of endpoint execution. A later event requesting the opposite
state must still be able to produce a new candidate. The memory design therefore
needs recent finalized state, not a long-term record of the project or device
\cite{wang2024surveyagents,liu2024lostmiddle}.

The selected window contains two completed interaction pairs, while synthetic
session identifiers isolate controlled sequences without changing the shared
sensor contract. It is process-local rather than restart-durable; leaving the
model-visible window does not imply physical deletion from backing history.
Section~\ref{subsec:impl-memory} describes the implementation mechanics.

\subsection{Structured Output and Shared Contract Boundary}\label{subsec:design-output}

The agent needs to express more than a shared action. In particular, it must
distinguish a requested state change from an already satisfied state and retain
state context that can support the next interaction. Placing these concepts in
the shared action schema would have changed the collaboration boundary.
Instead, \texttt{CONFIG-OBID} uses an internal decision envelope with five
fields: \texttt{decision}, \texttt{action}, \mbox{\texttt{state\_before}},
\mbox{\texttt{state\_after}}, and \mbox{\texttt{reason\_code}}.

For a state change, \texttt{decision} is \mbox{\texttt{emit\_action}} and the nested
\texttt{action} contains the unchanged four shared fields. For an already
satisfied state, \texttt{decision} is \mbox{\texttt{no\_action}} and \texttt{action}
is \texttt{null}. The latter is an internal representation of absent release;
\mbox{\texttt{no\_action}} is not a new action identifier. Table~\ref{tab:design-output-boundary}
shows the separation.

\subsection[Runtime Validation and Deterministic Policy]{Runtime Validation and\\Deterministic Policy}\label{subsec:design-safety}

Prompt constraints are useful for guiding the Decision Agent, but they are not
a release mechanism. A model can still return malformed JSON, omit a field,
use an unsupported value, or supply the wrong type. Minimal extraction is also
insufficient because successful parsing says nothing about conformance to the
full frozen action contract. RQ2 therefore requires independently observable,
post-agent controls \cite{wright2022jsonschemavalidation}.

The selected validator is contract-specific: an invalid candidate terminates
without repair or release. This is an ordering invariant, not a generic schema
platform or security filter; the executable checks are documented in
Section~\ref{subsec:impl-validator}.

Only a schema-valid action reaches deterministic policy. Policy applies the
frozen action/target allowlist and then distinguishes direct release, block, and
approval-required hold. This produces the stable outcomes \texttt{ALLOW},
\texttt{BLOCK}, and \mbox{\texttt{APPROVAL\_REQUIRED}} without asking another model to
judge whether its own output should proceed
\cite{schneider2000enforceable,wang2026agentspec}. Invalid candidates stop before
policy and before HITL, so a human cannot rescue an action that is outside the
shared contract. The detailed validation conditions and policy routing appear
in Sections~\ref{subsec:impl-validator} and~\ref{subsec:impl-policy}.

\subsection{Human-in-the-Loop Design}\label{subsec:design-hitl}

The inherited material described approval as a specification, but RQ2 asks
about runtime prevention and release. The selected design therefore includes an
executable HITL state rather than a documentation-only approval rule
\cite{amershi2019guidelines,dzindolet2003trust,nist2023airmf}. Entry is
conditional: the action must already be schema-valid, deterministic policy must
require approval, the four-field action must be held, and no action may already
have been released.

While an execution is pending, the held action is read-only review information
and no fan endpoint is eligible. Approval releases the unchanged stored action;
denial, invalid input, or an integrity mismatch releases nothing. The integrity
property is field equality, not a cryptographic guarantee.

The controlled approval context is supplied after validation; it is not
evidence that the Decision Agent autonomously discovers risk. Directly allowed
actions bypass HITL, while invalid candidates stop before it. The final gate
placement and integrity mechanics are documented in
Section~\ref{subsec:impl-hitl}.

\subsection{Evaluation-Oriented Design Decisions}\label{subsec:design-evaluation}

The architecture had to make failures and non-release observable before the
repeated evaluation was run. Otherwise, a missing endpoint call could not be
distinguished reliably from a transport failure, an input rejection, an
internal no-op, a validation block, a policy hold, or a human denial. The design
therefore exposes named terminal stages, candidate and release state, endpoint
eligibility, action-endpoint execution, simulated fan state, and stable run
identity. These observations support attribution; they do not change the shared
contracts.

Controlled seams isolate valid ingress, malformed pre-decision input, a known
post-agent candidate, and approval-required policy context. They are test
mechanisms rather than production interfaces or autonomous risk-discovery
components. Isolated sessions and stable identifiers connect each terminal to
its retained evidence. Sections~\ref{subsec:method-cases} and
\ref{subsec:impl-seams} define the cases and implementation details.

\subsection{Final System Architecture}\label{subsec:design-final}

Taken together, the selected components form one end-to-end path. A compatible
event reaches either the inherited \texttt{CONFIG-BASELINE} comparator or the
extended \texttt{CONFIG-OBID} configuration. In the latter, the Decision Agent
combines read-only calculation and observation with bounded model-visible
decision state. Any candidate is then subject to deterministic validation,
policy, and conditional HITL before authorized release to the inherited
simulated-fan path.

The processing stages retain the provenance boundary established in
Section~\ref{subsec:design-boundary}; integration does not merge authorship.

\subsection{Summary of Chosen Approach}\label{subsec:design-summary}

The chosen approach maps RQ1 to bounded state-aware decisions, RQ2 to executable
release controls, and RQ3 to two configurations at one shared boundary. The
scope decisions in Table~\ref{tab:design-alternatives} keep that architecture
attributable without treating excluded alternatives as inferior.
