\section{Introduction}\label{sec:intro}

\setlength{\emergencystretch}{2em}

\subsection{Background and Motivation}\label{subsec:intro-background}

IoT systems often transform sensor events into actions that change a device or
service \cite{perera2014context,ur2016triggeraction}. Workflow automation can
connect event intake, decision logic, and action execution in an inspectable
sequence \cite{vanderaalst2003workflowpatterns,bock2021lowcode}. A
language-model-based component
can make the decision stage responsive to event and state context rather than
only a fixed branch \cite{wang2024surveyagents}. Its output, however, remains a generated proposal and
cannot by itself be assumed to satisfy an interface contract or to be
authorized for release \cite{wright2022jsonschemavalidation,schneider2000enforceable}.

Reliability therefore concerns more than whether an action appears plausible.
Decision behaviour must be measured under defined conditions, while observable
runtime controls determine whether a proposal is contract-valid, permitted, or
subject to human approval before it reaches an action interface
\cite{amershi2019guidelines,dzindolet2003trust}. Such controls
also distinguish blocked, pending, failed, and released outcomes. This thesis
examines the problem through a bounded extension of an inherited n8n-based
workflow-to-action system in one defined IoT scenario, without seeking to
establish universal LLM reliability or production safety.

\subsection{Problem Statement}\label{subsec:intro-problem}

The inherited Yacoub-compatible system provides the event-to-action boundary,
middleware and action API, shared contracts, and a minimal-agent baseline. The
bounded problem is to investigate a stronger decision layer at the same
boundary: whether it produces expected actions across defined normal,
malformed, and state-dependent cases, and whether contract-invalid or
unapproved proposals are prevented from release. Compatibility must remain
intact so that reliability and latency can be compared fairly with the
inherited minimal agent. The technical and empirical challenge is therefore to
extend agentic behaviour while keeping the action vocabulary, system boundary,
and comparison conditions fixed.

\subsection{Aim}\label{subsec:intro-aim}

The aim is to design, implement, and evaluate a bounded n8n-based agentic
decision and reliability layer that extends the inherited Yacoub-compatible
workflow-to-action system while preserving the shared interface. The study
addresses expected-action accuracy and consistency, runtime validation,
deterministic policy and Human-in-the-Loop (HITL) control, and reliability and
latency differences from the inherited minimal-agent baseline. The inherited
implementation remains outside the contribution boundary described in
Section~\ref{subsec:intro-division}.

\subsection{Research Questions}\label{subsec:intro-rqs}

The study is guided by the following research questions:

\begin{description}
\item[RQ1.] How accurately and consistently does the extended n8n-based
agentic decision layer produce the expected IoT action across defined normal,
malformed, and state-dependent test cases?

\item[RQ2.] How effectively do runtime structured-output validation,
action policies, and Human-in-the-Loop approval prevent invalid or risky agent
actions from reaching the shared IoT action interface?

\item[RQ3.] What reliability and latency differences are observed
between the inherited minimal agent baseline and the extended Obid agentic
workflow under the same defined IoT test cases?
\end{description}

\subsection{Scope and Delimitations}\label{subsec:intro-scope}

The study covers one temperature-to-fan scenario, one primary model
configuration, one Decision Agent, exactly two read-only tools, one
bounded-memory configuration, and one simulated fan target. It preserves the
inherited middleware boundary and Yacoub-originated shared contracts, and uses a
controlled repeated evaluation under frozen cases. Excluded are production
deployment, generic safety or cybersecurity assurance, new physical Obid
Raspberry Pi or GPIO validation, broad multi-agent architecture, the deferred
validator-agent comparison, multiple models, memory strategies or devices,
scalability benchmarking, and statistical generalization. The study thus
evaluates one bounded Obid extension against one inherited comparator in one
simulated setting. Earlier physical evidence remains inherited context.

\subsection{Contributions}\label{subsec:intro-contributions}

The Obid contribution has three parts. The cognitive contribution is a stronger
single-agent workflow with read-only tools, bounded memory, controlled
ReAct-style execution, and structured internal decisions. The runtime
reliability contribution places contract-specific validation, deterministic
policy, and executable HITL before release to the shared interface. The
evaluation contribution is a frozen repeated comparison with the inherited
minimal agent, with retained failures, locked raw data, deterministic
processing, and traceability to execution evidence. These are Obid-created
contributions; the inherited context and infrastructure remain outside the
authorship claim summarized in Section~\ref{subsec:intro-division}.

\subsection{AI Tool Use and Disclosure}\label{subsec:intro-ai-disclosure}

AI tools were used occasionally as support during the project, mainly for
improving language, structuring parts of the report, and providing limited
technical assistance when needed. They were not used as a substitute for the
actual project work. The research scope, design choices, implementation,
evaluation, and interpretation of the results were carried out and verified by
the author. Any AI-generated suggestions or text were reviewed before being
included in the thesis.

\subsection[Division of Work and Collaboration Boundary]{Division of Work and\\Collaboration Boundary}\label{subsec:intro-division}

The thesis studies one integrated system with separately attributable work.
Yacoub originated the workflow-to-action infrastructure, middleware and action
API, threshold/action and baseline semantics, and earlier Raspberry
Pi/action-side evidence. The inherited implementation is
\mbox{\texttt{YACOUB\_INHERITED}}; the Yacoub-originated contracts are
\mbox{\texttt{SHARED\_INTERFACE}}, whose shared use does not imply joint
authorship. Obid's extended decision and reliability layer, runtime controls,
HITL, evaluation, and new evidence are \mbox{\texttt{OBID\_CREATED}}.
Reproducing or evaluating inherited work does not transfer its implementation
authorship, while new observations remain Obid-created evidence even when they
describe the inherited comparator. Earlier physical evidence remains inherited
context rather than Obid hardware validation.
